Migration: Add `customer_uid` and `phone_numbers` table

Overview
--------
This migration adds a stable `customer_uid` (UUID) to `sarga_customers` and creates
a dedicated `phone_numbers` table to support multiple numbers per customer and
store normalized E.164 values.

High-level steps
----------------
1. Backup your database.
2. Run the SQL: [server/migrations/2026_04_17_add_customer_uid_and_phone_numbers.sql](server/migrations/2026_04_17_add_customer_uid_and_phone_numbers.sql).
3. Install dependencies and run the backfill script to compute E.164:

```bash
cd "D:\software sarga"
npm install google-libphonenumber mysql2
DB_HOST=localhost DB_USER=root DB_PASS=yourpass DB_NAME=sarga node server/scripts/backfill_phone_numbers.js
```

4. Inspect conflicts (if any): `server/migrations/phone_conflicts_2026_04_17.json`.
   - Resolve duplicates and decide which customer should keep the number.
   - Manually update `phone_numbers` rows and set `is_primary = 1` on the chosen number.

5. Update application code to:
   - Accept and prefer `customer_uid` for external APIs/internal references.
   - Use `phone_numbers.number_e164` for lookups when normalized numbers are available.
   - During transition, keep supporting old `mobile` lookups (map to `phone_numbers`).

6. Optional later step: after thorough testing and rollout, consider removing
   the UNIQUE constraint on `sarga_customers.mobile` and stop writing directly
   to `sarga_customers.mobile` — use `phone_numbers` instead.

Notes & Caveats
---------------
- The SQL seeds `phone_numbers` with raw mobile values; the Node script normalizes
  them and writes `number_e164`.
- The migration preserves `id` (integer PK) — we add `customer_uid` to enable
  a gradual move to UUIDs for external identifiers.
- If you prefer numeric surrogate IDs rather than UUIDs, adjust the SQL to add
  a `customer_slug` or `external_id` BIGINT AUTO_INCREMENT column and populate accordingly.
